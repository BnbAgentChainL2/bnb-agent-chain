### 1.3 发射前必须全绿的三项（`01-CONTRACT-SPEC.md` §9 步骤 ⑨）

**任一项不过，绝不允许打开发射表单。**

1. `BacBridge.bacToken() == BacNodeFund.bacToken() == ValidatorStaking.bacToken() == T`，
   其中 `T` 是**当场重新用 `cast create2` 算出来**的地址，不是从环境变量里读的缓存值；
2. `cast code T` 为空，且 `Portal.getTokenV8Safe(T)` revert（这个地址还没被别人占）；
3. `Portal` 上这个 salt 的锁定记录属于 `LAUNCHER`（`Portal.getSaltLock(salt).locker == LAUNCHER`）。

这三项就是 `scripts/sim_launch.sh` 开头的「factory pre-checks / token-immutable pre-checks」段落，

## 2. 全新部署钱包

### 2.1 为什么必须是新的

部署钱包在链上会被永久记录成这七个合约的部署者，任何人都能顺着它翻出你所有的历史交易。
**用一个从来没用过的地址**，不要用平时买卖币的钱包，也不要用以前的项目用过的那个。

生成方式（选一种，**都不要把私钥写进仓库**）：

```bash
# 硬件钱包里新派生一个地址（推荐；DeployBac 支持 --ledger / --trezor）
# 或者本机生成一个一次性热钱包：
cast wallet new           # 打印地址和私钥；私钥只存进系统密钥链或本机 .env（.env 已在 .gitignore 里）
```

**[需要用户确认]** 部署钱包地址定下来之后就不能换了 —— `BacVaultFactory.LAUNCHER` 是 immutable，
`ChainAnchor.bridge()` 用的是按**部署钱包的 nonce** 预测出来的地址。换钱包 = 整轮重部。

### 2.2 充多少 BNB

| 项目 | 金额 | 说明 |
|---|---|---|
| 七笔部署交易 | **待测**（下界约 0.001 BNB @ 0.05 gwei） | 跑 `scripts/anvil_rehearsal.sh` 拿真实值，填进这里 |
| `Portal.lockSalt(salt, TOKEN_TAXED_V3)` | **正好 0.01 BNB** | 2026-09-23 在主网用 `eth_call` 实测（`SaltLockFeeMismatch` 把要价回吐出来），约 150,641 gas |
| `ChainAnchor.setValidatorStaking` + `AgentRegistry.setVaultSink` | 两笔小交易，可忽略 | |
| 发射交易本身 | gas + **你的首买金额** | flap.sh 不另收发射费；`msg.value` 就是首买 |
| **运营者初始浮动（`OPERATOR_FLOAT` = 1,000 BAC）** | **待定** | 创世前必须在 `BacBridge` 里锁 1,000 BAC，否则中继在层内的 1,000 BAC 创世余额没有 1:1 背书（硬停第 14 项）。这 1,000 BAC 要**在市场上买**，价格取决于曲线，还要付 2% 买税 |

**[需要用户确认]** 首买金额、以及买 1,000 BAC 运营浮动的时机（发射当天买，还是等曲线跑一段再买）。

## 3. BSC 侧部署（`01-CONTRACT-SPEC.md` §9 的 ①–⑩）

顺序不能改。④ 和 ⑦ 互相引用（`ChainAnchor` 要桥地址、`BacBridge` 要锚点地址），
解法是先部 `ChainAnchor`、构造参数里填**按 nonce 预测出来的**桥地址，部完再回读核对。

```
①  挖 …7777 靓号 salt，并【需要用户确认】立刻 Portal.lockSalt(salt, 6) —— 花 0.01 BNB
②  BacVaultUI 链接库（CREATE2 salt 0；字节码与 fly / rat 不同，不会撞地址）
③  AgentRegistry(admin, vetoKey)
④  ChainAnchor(预测的 BacBridge, relayer, admin, vetoKey, initialCirculating = 1000e18)
⑤  ValidatorStaking(T, anchor, admin)
⑥  BacNodeFund(T, 冷钱包 owner)
⑦  BacBridge(T, registry, anchor, watchdog)   ← 必须正好落在 ④ 里预测的那个地址
⑧  ChainAnchor.setValidatorStaking(⑤)          ← 一次性，只有部署者能调
⑨  发射前硬停三项（§1.3）全绿
⑩  BacVaultFactory(launcher)                   ← beacon 和金库实现在构造函数里造，绝不在脚本里造
```

**① 的 `lockSalt` 为什么不能省：**`bacToken` 是 ⑤⑥⑦ 三个合约的 **immutable**，值是本地预测出来的 `T`。
只要发射表单里的 salt 不是逐字同一个（flap.sh 自己挑了个靓号、页面被重开、或者有人在 ⑦ 和 ⑪ 之间把这个地址占了），
VaultPortal 预测出来的 `taxToken` 就不是 `T`，`newVault` 当场 revert `"Bridge is bound to another token"`。
**没有任何补救路径**：三个 immutable 逼着 `BacBridge` + `BacNodeFund` + `ValidatorStaking` 重部，
而重部 `BacBridge` 又让 ④ 的预测失效、⑧ 的一次性写入也已经用掉 —— **四个合约、一整轮全部作废**。

### 3.1 先干跑，再广播

```bash
export BSC_RPC_URL=https://bsc-rpc.publicnode.com
export BAC_ADMIN=0x… BAC_VETO_KEY=0x… BAC_RELAYER=0x… BAC_WATCHDOG=0x…
export BAC_NODE_FUND_OWNER=0x… BAC_LAUNCHER=0x… BAC_TOKEN_PREDICTED=0x…7777
export BAC_DEPLOYER_ADDRESS=0x…

cd contracts
# 干跑：forge 什么都不发
forge script script/DeployBac.s.sol:DeployBac --rpc-url "$BSC_RPC_URL" --sender "$BAC_DEPLOYER_ADDRESS"
```

干跑输出里逐条核对：`T` 没有代码、`ChainAnchor.bridge()` 等于随后部出来的 `BacBridge`、
`BacVaultFactory.LAUNCHER()` 等于 `BAC_LAUNCHER`、`beacon.owner()` 等于工厂本身。

**[需要用户确认] 真正广播（不可逆）：**

```bash
BAC_BROADCAST=I_HAVE_READ_SECTION_9 \
forge script script/DeployBac.s.sol:DeployBac --rpc-url "$BSC_RPC_URL" \
  --sender "$BAC_DEPLOYER_ADDRESS" --broadcast --slow
# 私钥用 --ledger / --trezor / --interactive，不要写进命令行、不要写进 .env 再 echo
```

脚本自己有闸：只给 `--broadcast` 而没有那个环境变量，它会 revert。

### 4.2 `vaultData` 三个字段（工厂的 `vaultDataSchema()` 逐字渲染出来的）

flap.sh 会读 `factory.vaultDataSchema()` 自动生成这三个输入框。**顺序就是下面这个顺序**，
三个都是 `address`、`decimals = 0`，页面不会替你乘任何倍数。

| # | 字段名 | 类型 | 填什么 | 表单上会显示的说明（合约里逐字写死的） |
|---|---|---|---|---|
| 1 | `owner` | `address` | 你的冷钱包，或 `0x0000000000000000000000000000000000000000` | 「Vault owner. It has no power to move any funds; leave 0x0 to use the launching wallet. / 金库 owner。它没有任何动用资金的权力；填 0x0 则为发射钱包。」 |
| 2 | `bridge` | `address` | §3 步骤 ⑦ 部出来的 **`BacBridge`** | 「BacBridge address (holds the bridge pool). / BacBridge 地址（持有桥池）。」 |
| 3 | `nodeFund` | `address` | §3 步骤 ⑥ 部出来的 **`BacNodeFund`** | 「BacNodeFund address (holds the official node fund). / BacNodeFund 地址（持有官方节点基金）。」 |

**这三个地址一个都不能填错，也不能对调。** 工厂会当场查：

- 两个地址都非零、互不相同 → 否则 `"Bad bridge or node fund / 桥或节点基金地址无效"`
- 两个地址都有代码 → 否则 `"Bridge or node fund has no code / 桥或节点基金不是合约"`
- `IBacBridge(bridge).bacToken() == taxToken` → 否则 `"Bridge is bound to another token / 桥绑定的是别的代币"`
- `IBacNodeFund(nodeFund).bacToken() == taxToken` → 否则 `"Node fund is bound to another token / 节点基金绑定的是别的代币"`
- `creator == LAUNCHER` → 否则 `"Launcher not allowed / 该地址不能用此工厂发射"`

填 `owner = 0x0` 的含义：金库 owner 变成发射钱包。**注意 `owner` 和「谁能提节点基金」是两回事** ——
提节点基金的是 `BacNodeFund.owner()`（§1.4 里那个冷钱包），金库的 `owner()` 对任何资金都没有权力。
金库的 `description()` 会把这两个地址**分别**渲染出来，`verify_launch.py` 的第 13 项专门核对这一点。

## 8. 层内链上线（bring-up）

顺序是死的：**BSC 合约 → 用真实地址生成创世 → 起 Besu → 起中继 → 起索引器 → 网站指过去。**
每一步都有一件必须当场验证的事，不验证就不许进下一步。

### 8.0 为什么必须是这个顺序

层内 `L2Bridge` 的 `BSC_BRIDGE` 是 **immutable，烧进创世字节码**。创世文件一生成、链一启动，
这个地址就**永远改不了**。所以必须先有 BSC 侧的 `BacBridge` 地址，才能生成创世。
反过来做 = 整条链作废，只能换 chainId 重来。

### 8.1 步骤

| 步 | 动作 | 做完必须验证什么 | 不可逆？ |
|---|---|---|---|
| 1 | §3 的 BSC 侧部署 + §6 的发射 + §7 的 14 项核验全过 | `verify_launch.py --phase launch` 退出码 0 | 是 |
| 2 | **买 1,000 BAC 并锁进 `BacBridge`**（`OPERATOR_FLOAT`） | `BacBridge.totalCreditsIssued() >= 1000e18` | **[需要用户确认]** 锁进去的 BAC 永久锁死 |
| 3 | 确定创世时间戳 `BAC_GENESIS_TS`（一个 UTC 整点午夜）和中继层内地址 `RELAYER_LAYER_ADDR` | 中继地址的私钥在服务器上、且只在服务器上 | 是（写进创世） |

### 8.2 每一步的失败长什么样

- **第 6 步 storage 不为零** → 某个系统合约的构造函数写了存储。创世里的合约是**没有构造函数**的，
  写了就意味着上链之后那个槽是 0 而本地是非 0。必须改合约，回到第 4 步。
- **第 8 步块 0 哈希对不上第 7 步** → 起链用的不是我们生成的那个文件。**立刻停机**，不要让它继续出块。
- **第 9 步 L3 不过** → 层内 `L2Bridge.BSC_BRIDGE()` 指向别的合约。整条链作废（immutable 改不了），
  换 chainId 重来；BSC 侧不受影响。
- **第 9 步 L4 报 FeeSplitter 没代码** → §0-c 没做完就生成了创世。创世里没有代码的地址**永远加不上代码**，
  整条链作废。
- **第 10 步锚点提不上去** → 先看 `ChainAnchor` 的 revert 串。最常见的是 `"Commit window not closed"`
  （纪元刚结束就提交）和超发（`cumulativeCredited + credited > BacBridge.totalCreditsIssued()`）。

### 9.1 谁能动钱

- **桥池那一半：谁都动不了。** 金库没有 owner 提款、没有紧急提款、没有救援函数；金库 owner 和 Flap Guardian

```bash
RPC=https://bsc-rpc.publicnode.com
NODEFUND=0x…
cast call $NODEFUND 'balance()(uint256)'            --rpc-url $RPC   # 可提余额
cast call $NODEFUND 'owner()(address)'              --rpc-url $RPC   # 谁能提（网站和横幅上写的就是它）
# 提款要 owner 冷钱包签名；私钥不要出现在命令行、日志或聊天里
```

- **`settle()` / `retryPush()` 无许可、无参数、调用者一分钱拿不到。** 两次 settle 之间金库里会留着没分账的零头，
  这是正常的，`accountedQuote()` 就是它。监控里有一条：**连续 2 个纪元 `accountedQuote()` 非零且单调上升**
  = 没人在调 `settle()`，我们自己调一下。

### 9.2 必须一直跑的对拍

- 每小时：`TaxProcessor.marketAddress() == vault`。不一致 → 网站挂红条 + **停止一切宣传**。
- 每天：重跑一次 `verify_launch.py --phase genesis`，尤其看第 11 项 `state()` 有没有变成 `TaxFree`
  （这是 `taxDuration` 填错的**唯一**可观测信号，而且一旦出现就无法挽回）。
- 监控告警清单见 `02-CHAIN-SPEC.md` §5.4 与 `00-DESIGN-SPEC.md` §7.1。
